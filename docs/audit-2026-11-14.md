# Полный аудит приложения — 2026-11-14

Методика: 4 параллельных субагента (архитектура, безопасность, данные/надёжность,
сборка/зависимости) + верификация ключевых находок по исходникам. Все P0-утверждения
подтверждены вручную, если не указано иное.

**Модель развёртывания (уточнена владельцем):** публичный HTTPS-хостинг на
собственном домене **https://shedule.rgsu.by**. Это снимает прежнее противоречие
«LAN без HTTPS vs PWA»: secure context есть, SW/PWA/push работают как спроектированы
(`metadataBase` уже указывает на этот домен). Но угроза смещается: приложение
доступно **всему интернету**, поэтому открытые API-эндпоинты и слабая
debug-аутентификация становятся острее, чем в LAN-сценарии.

Сервер: собственный хостинг владельца (Node-процесс, API-роуты + push обязательны).

---

## Исполнительное резюме

Проект зрелый: чистый tsc, продуманный серверный кэш с inflight-дедупликацией и
ETag/304, дисциплина токенов и движения, аккуратные комментарии-обоснования,
корректные server/client границы. Главные проблемы:

1. **Зависимости с critical-уязвимостями** (next RCE, jspdf) — лечится двумя
   командами npm в рамках текущих semver-диапазонов.
2. **Открытые API-эндпоинты** — `/api/push/test` (рассылка пуша всем), `/api/push/check`
   (выжигание квоты Sheets), `/api/push/subscribe` (SSRF) — теперь доступны
   интернету, не только внутренней сети.
3. **Отсутствие отказоустойчивости перед Google Sheets** — единственный источник
   данных без таймаута, retry и stale-fallback; сбой сети = 500 всем или зависший
   API до перезапуска.
4. **Debug-аутентификация** не выдержит публичного размещения (слабый пароль,
   нет rate limit, replayable cookie).
5. **Балласт**: мёртвый код (~800 строк), мёртвые зависимости, три конфликтующих
   деплой-таргета.

## P0 — сделать до выката на публичный домен

### 1. Critical-уязвимости в runtime-зависимостях
`package.json` — `next@16.1.6`, `jspdf@4.1.0`. npm audit (prod-граф): 2 critical,
12 high. **next** — ~35 advisories, включая **unauthenticated RCE на Windows-хостах
(CVSS 9.0, GHSA-p293-qw3h-jr36)** и SSRF/Middleware bypass — для self-hosted
Node-сервера, доступного из интернета, это прямой сценарий. **jspdf** — HTML
injection (CVSS 9.6), object injection; используется на клиенте (экспорт PDF).
**Решение:** `npm update next jspdf` (фиксы входят в диапазоны: next ≥16.4.1,
jspdf ≥4.2.0), перепроверить `npx tsc --noEmit` и сборку.

### 2. `/api/push/test` без авторизации — рассылка пуша всему интернету
`app/api/push/test/route.ts:7-14` — GET без проверок рассылает пуш **всем**
подписчикам в Redis. На публичном домене любой человек из интернета может
устраивать массовый спам на устройства всех подписчиков.
**Решение:** `isDebugAuthorized()` (как у `/api/debug/chat`) или Bearer-секрет;
если маршрут нужен только для отладки — отключить в проде.

### 3. `/api/push/check` без cron-секрета и мимо кэша
`app/api/push/check/route.ts:16-21` — ничем не защищён и вызывает `loadSchedule()`
напрямую в обход 60-с кэша `utils/scheduleCache.ts` → квота Google Sheets
(~60 req/min) выжигается скриптом за секунды **из интернета**; побочно —
перезапись снапшота и триггер ложных рассылок.
**Решение:** проверка `Authorization: Bearer ${CRON_SECRET}` в начале GET +
переход на `getSchedule()`. Cron по-прежнему внешний (cron-job.org уже
упомянут в README — на публичном домене он достучится), просто добавить секрет
в его заголовки.

### 4. Google Sheets — SPOF без таймаута, retry и stale-fallback
`utils/loadSchedule.ts:36-39` — `sheets.spreadsheets.values.get()` без `timeout`
и retry; `utils/scheduleCache.ts:37-57` — при ошибке исключение пробрасывается,
хотя stale-запись `entry` могла остаться; «сетевая чёрная дыра» (hang, не refuse)
блокирует единый `inflight`-промис → API не отвечает всем до перезапуска Node.
Пустой ответ (`rows.length === 0`) кэшируется на 60 с → все клиенты получают
«Расписание не опубликовано».
**Решение:** (а) `timeout: 10000, retry: { retries: 2 }` в конфиге gaxios;
(б) stale-on-error — при ошибке возвращать устаревший `entry` с флагом `stale`;
(в) `lastGoodEntry` в памяти процесса без TTL; (г) пустой результат не кэшировать.

### 5. SSRF через `/api/push/subscribe`
`app/api/push/subscribe/route.ts:19-26`, `lib/push-utils.ts:80-82` —
`subscription.endpoint` не валидируется ни по схеме, ни по хосту: сервер можно
заставить POST-ить на любой адрес (внутренние сервисы хостинга, облачные
метаданные 169.254.169.254). `keys.p256dh/auth` не проверяются на формат.
**Решение:** whitelist схем `https://` и хостов push-сервисов
(fcm.googleapis.com, updates.push.services.mozilla.com, web.push.apple.com),
валидация base64url ключей, ограничение частоты подписок на IP.

### 6. Id записей = индекс строки Sheets
`utils/loadSchedule.ts:54` (`id: ${index + 1}`) + `lib/schedule-utils.ts`
(`createItemKey` предпочитает `item.id`). Вставка/перестановка строк деканатом →
сдвиг всех id → `compareScheduleData` видит «всё удалено + всё добавлено» →
шторм ложных тостов у всех клиентов + ложные push-рассылки.
**Решение:** ключ по содержимому `date|time|group|subject|teacher|classroom|lessonType`
или хеш содержимого строки; `id` в сравнении не использовать.

### 7. Debug-аутентификация не выдержит публичного домена
`lib/debug-auth.ts`, `app/actions/debug-auth.ts`. Пароль в .env — **5 символов**
(интернет-брутфорс тривиален); на `loginAction` нет rate limit; сравнение не
constant-time; cookie — несолёный `sha256(DEBUG_PASSWORD)` — детерминированное
значение, пригодное для replay при перехвате; 24 ч без отзыва.
Уточнение верификации: автооткрытие в dev (`isOpenWithoutPassword`) срабатывает
только при **отсутствии** `DEBUG_PASSWORD` — с текущим .env dev закрыт паролем.
Но **на публичном хосте dev-режим запускать нельзя никогда** (`next dev -H 0.0.0.0`
без .env = /debug и AI-прокси с серверным ключом открыты миру); только
`next build` + `next start`.
**Решение:** пароль ≥12 символов; `crypto.timingSafeEqual`; rate limit
(Redis/in-memory, N попыток / 15 мин на IP); сессионный токен (случайный, хеш
в Redis с TTL) вместо хеша пароля. Secure-cookie поверх HTTPS работает корректно —
этот пункт снят.

## P1 — важно

8. **`/api/calendar/[group]` и `/api/push/check` минуют кэш**
   (`calendar/route.ts:52`, `check/route.ts:14`) — каждый запрос = вызов Sheets
   API; 50 календарных подписок утром = упор в квоту. Решение: перейти на
   `getSchedule()` (`revalidate=300` в calendar поверх станет дешёвым).
9. **`matchesFilters`: подписка «на всё» никогда не получает уведомления**
   (`lib/push-utils.ts:114-120`) — комментарий обещает «пустые фильтры → всё»,
   код возвращает `false`. **Решение владельца (14.11): подписки «на всё» быть
   не должно** — уведомления только о выбранной группе/преподавателе; прав
   код, а не комментарий. Внедрено: комментарий приведён к замыслу;
   `/api/push/subscribe` отклоняет пустые фильтры (400); тумблер без выбора
   показывает тост-подсказку вместо тихого no-op.
10. **Ошибка SWR замещает весь UI** (`components/DynamicSchedule.tsx:266-277`) —
    при `error` с валидными `data` рендерится полноэкранный `ScheduleError`
    вместо устаревшего расписания. Решение: `ScheduleError` только при
    `error && !schedule`; иначе данные + баннер «данные могли устареть»;
    `keepPreviousData` для смены группы.
11. **Нет error boundary; битая дата роняет «Месяц»**
    (`components/month-schedule-view.tsx:60-64` — `format(Invalid Date)` кидает
    RangeError). Решение: `isValid(d)` + `continue` со счётчиком для /debug;
    корневой `app/error.tsx` с retry.
12. **Redis — облачный Upstash; деградации нет** (`lib/push-utils.ts:6-9`,
    `lib/debug-ai-limit.ts:20-31`): при недоступности Upstash подписки пуша,
    снапшот и лимиты AI падают 500 без fallback (fallback в ai-limit срабатывает
    только при отсутствии env). Для публичного хостинга Upstash допустим, но
    нужна обёртка `safeRedis()` с try/catch и in-memory fallback + лог «degraded».
13. **Отсутствуют security-заголовки** (нет `headers()` в `next.config.mjs`, нет
    middleware). Решение: `X-Content-Type-Options: nosniff`,
    `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`,
    базовый CSP (`default-src 'self'` с исключениями для inline-скриптов Next).
14. **ICS-инъекция** (`app/api/calendar/[group]/route.ts:76`) — `group` из URL
    попадает в `X-WR-CALNAME` без `escapeIcsText` → `%0A` дописывает строки в
    VCALENDAR (фишинг через календарь — распространение вредоносной ссылки
    публичному домену ничем не мешает). Решение: экранировать itemName,
    вырезать `\r\n` из всех полей.
15. **Скрипт `lint` сломан в Next 16** (`package.json:10`) — `next lint` удалён,
    команда падает. Решение: `"lint": "eslint ."` (flat config уже стоит).
16. **Дрейф структуры lib/ vs utils/ vs hooks/** — серверные модули в двух местах
    (`utils/` — loadSchedule, scheduleCache; `lib/` — push-utils, debug-auth,
    debug-ai-*), хуки в двух местах (`lib/use-swipe-navigation.ts`,
    `hooks/use-mobile.tsx`). Решение: конвенция «lib/ — изоморфное/клиентское,
    hooks/ — все хуки, utils/ — серверный слой»; перенести push-utils, debug-*
    в utils/, use-swipe-navigation → hooks/.
17. **Расщеплённый источник истины группы/преподавателя** — localStorage + URL +
    state; XOR-логика «группа или преподаватель» продублирована в 5 местах
    (`DynamicSchedule.tsx:101-124`, `schedule-view.tsx:131-152,200-214,302-318`,
    `NotificationSettings.tsx:64-70`). Решение: `lib/selection-storage.ts`
    (read/write/clear + нормализация) или мини-стор на SWR.
18. **Три конфликтующих деплой-таргета** — `netlify.toml` +
    `@netlify/plugin-nextjs` в devDependencies, скрипт `cf:build` (Cloudflare),
    следы Vercel в комментариях. Целевой таргет теперь один — собственный хостинг
    под shedule.rgsu.by. Решение: удалить netlify/cf-артефакты; задокументировать
    развёртывание (`next build && next start`, процесс-менеджер + reverse-proxy
    с TLS).
19. **Артефакты SW в репо** — `public/sw.js`, `public/workbox-*.js`,
    `public/swe-worker-*.js`, `public/custom-sw.js` (от 21.10 — устаревшая копия
    `worker/index.ts`; push-обработчики существуют в двух местах) в git.
    Решение: добавить в `.gitignore`, `git rm` разово; источник — только
    `worker/index.ts`.

## Вердикт архитектора (сводка)

Зрелый проект с продуманными деталями (серверный кэш с дедупликацией и ETag,
разделение лёгкой `/api/schedule/meta` от тяжёлой `/api/schedule`, дисциплина
токенов и движения через `lib/motion.ts`, корректные server/client границы,
middleware не нужен). Три системные проблемы:

1. **Безопасность публичной поверхности** — открытые push-эндпоинты, слабая
   debug-аутентификация, отсутствующие заголовки. Приложение изначально
   проектировалось под публичный домен (metadataBase = shedule.rgsu.by), но
   защитный контур под этот сценарий не достроен.
2. **Накопленный балласт** — два файла-дубля, мёртвая таблица на 548 строк, две
   мёртвых UI-библиотеки, мёртвая анимационная экосистема, фиктивные пакеты,
   три конфликтующих деплой-таргета. Раздувает поверхность сопровождения и
   вносит ложные сигналы «как тут принято».
3. **Дрейф структуры** — серверный слой размазан lib/utils, хуки в двух местах,
   источник истины выбора группы в 5 местах с дублями XOR-логики. Для текущего
   масштаба работает; при росте (новые типы расписания, аудитории) начнут
   трещать `ScheduleItem`-как-строки и клиентские фильтры поверх серверных.

Крупные файлы: `ai-chat.tsx` 1188, `VirtualScheduleTable.tsx` 518,
`debug-checks.tsx` 510.

Что работает хорошо: серверный кэш с inflight-dedup + ETag/304, серверная
фильтрация по группе (клиенту едет только его часть), явная сортировка внутри
дня везде (`mergeGroupLessons`), SW-правила (NetworkOnly для /debug, отдельный
слот meta), динамические импорты jspdf, `lib/clipboard.ts` с фолбэком,
виртуализация таблицы корректна.
